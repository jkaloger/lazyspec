## Changes

### 1. Surgical remote merge for ordinary relations on the issue store (`src/engine/store_dispatch.rs`)
- ROOT CAUSE: ordinary `link`/`unlink` (non-native, e.g. `implements`/`blocks`) of a github-issues source rewrites cache `related`, then `push_if_github_backed` (`src/cli/link.rs:104,342`) -> `GithubIssuesStore::push_cache` (`:166`) -> `check_lock` (`:251`). `check_lock` (`:270`) bails `"{} has been modified on GitHub since your last fetch."` (`:271-279`) when `remote_issue.updated_at != local_updated_at`. Out-of-band remote bump (comment) -> guard fires -> ordinary relation write rejected EVEN THOUGH the relation edit doesn't contend the body (defect A,D). UNLIKE native (STORY-167/ITER-222), the ordinary `related` IS round-tripped into the GitHub body (`issue_body::serialize` `:49-54` emits `related:`). So `push_cache`'s whole-cache re-serialize is a CLOBBER: it overwrites remote body (prose + any remote-added relations) with stale local cache -> can't just drop the lock (defect A: would lose remote prose).
- FIX = surgical 3-way-ish merge on remote, NOT whole-cache push. ADD `pub fn merge_relation_to_remote(&mut self, type_def: &TypeDef, doc_id: &str, rel_str: &str, target_id: &str, set: bool) -> Result<()>` next to `push_cache` (`:166`)/`resync_after_native_edge` (`:202`). Body:
  - resolve `issue_number` from `self.issue_map.get(doc_id)` directly (NOT `check_lock` -- no reject path).
  - `issue_view` remote ONCE -> `remote_issue` (current `updated_at` + body + title/labels/state).
  - build `IssueContext` from remote (`title`, `labels` -> tags, `is_open = state=="OPEN"`) + `type_def.attr_defs`/`known_types`/`default_type` -- COPY the shape at `update` (`:870-883`).
  - `let (mut remote_meta, remote_prose) = issue_body::deserialize(&remote_issue.body, &ctx)?` (`:83`) -> remote prose preserved (defect A).
  - apply delta to `remote_meta.related`: `set==true` -> insert-if-absent `Relation { rel_type: RelationType::new(rel_str), target: target_id }` (NO push when `(rel,target)` already present -> dedup, defect C); `set==false` -> retain-filter drop matching `(rel_str,target_id)` (mirror unlink retain at `src/cli/link.rs:311-320`).
  - `let new_body = issue_body::serialize(&remote_meta, &remote_prose)` (`:32`) -> `issue_edit(&self.repo, issue_number, None, Some(&new_body), &[], &[])` (`:177` shape).
  - record remote `updated_at`: `self.issue_map.insert(doc_id, issue_number, &remote_issue.updated_at, &remote_issue.id)` (like `resync_after_native_edge` `:224-229`, NOT cleared like `push_cache` `:181`); `issue_map.save`; `issue_cache.touch_lock(doc_id)`.
  - NO `check_lock`, NO bail-on-stale on this path.
- DECISION: dedicated delta method, NOT generalize `resync_after_native_edge` (that re-mirrors LOCAL cache body; ordinary needs the REMOTE body deserialize + targeted edge edit to keep remote prose). LEAVE `push_cache` + `check_lock` UNCHANGED -> ordinary `update`/`set_provenance`/`delete` body writes (`:867,999,1042`) keep optimistic lock. NOT removing the lock globally (out of scope).

### 2. Plumb the relation delta + push-first ordering into `link_inner`/`unlink_inner` (`src/cli/link.rs`)
- `push_if_github_backed` (`:351`) currently takes `native_edge: bool` only; ordinary path -> `push_cache` (`:420`). EXTEND signature with the delta `(rel_str: &str, target_id: &str, set: bool)` (and keep `native_edge`). Dispatch (`:414-421`):
  - `if native_edge { gh_store.resync_after_native_edge(type_def,&doc_id) }`  (UNCHANGED, ITER-222)
  - `else { gh_store.merge_relation_to_remote(type_def,&doc_id,rel_str,target_id,set) }`  (NEW ordinary path -> no lock, surgical merge)
- PUSH-FIRST (defect D): currently `link_inner` frontmatter write (`:71-85`) PRECEDES push (`:104`); a failed push leaves cache already mutated (cache != remote). REORDER `link_inner`:
  1. resolve `rel_str`/`from_id`/`to_id`/`resolved_from` (`:64-70`, unchanged).
  2. `let native = apply_native_milestone(..)? || apply_native_membership(..)?;` (`:87-103`, unchanged -- native PATCH is its own authoritative write).
  3. `push_if_github_backed(root,&resolved_from,Some(config),client_factory, native, &rel_str, &to_id, true)?` FIRST -> remote merged (or native resync). On `Err`, return BEFORE touching cache (defect D: failed push leaves cache unchanged).
  4. ONLY on push success: `rewrite_frontmatter` cache `related` (`:71-85` body) -- insert-if-absent the `(rel_str,to_id)` entry so cache == merged remote (dedup, defect C).
  5. `push_if_git_ref_backed(..)` (`:105`, unchanged -- git-ref never hits the issue guard).
- INSERT-IF-ABSENT on the cache write (defect C): the `:75-83` push always-appends; gate it -> skip when `related` already carries a mapping `{rel_str: to_id}`. So a double-`link` is a no-op on disk AND on remote (merge step in §1 already skips the remote `issue_edit`).
- SYMMETRIC on `unlink_inner` (`:288`): same reorder -- native/merge push FIRST (`set=false`), then on success retain-filter the cache `related` (`:310-322` body). `merge_relation_to_remote(..,set=false)` retain-drops on remote. Failed push -> cache unchanged.
- NOTE: native path (`native==true`) keeps its OWN ordering nuance -- the field PATCH (`apply_native_*`) is the edge of record and stays authoritative/last-write-wins (ITER-222); the cache mirror follows. For native, frontmatter-then-resync ordering is acceptable (resync can't reject). The push-first reorder is the ORDINARY-path fix; keep native behavior as ITER-222 shipped it (resync after the field PATCH).

## Notes

- INVARIANT (defect A,D): after a successful ordinary `link`/`unlink`, cache `related` == remote `related`, AND remote prose is never clobbered, regardless of unrelated remote `updated_at` advances. The contended object is the issue BODY (prose); the relation delta is surgical (insert/remove one edge on the deserialized remote `related`), so it composes with concurrent remote prose edits WITHOUT a body-staleness reject.
- WHY merge not lock-drop: ordinary `related` lives IN the GitHub body (`issue_body::serialize` `:49-54`), so dropping the lock + `push_cache` would overwrite remote prose with stale cache (defect A). Native `related` is NOT in the body (the edge of record is the milestone field / Projects v2 item), so ITER-222 could safely re-mirror local cache via `resync_after_native_edge`. Two policies, two methods: `merge_relation_to_remote` (ordinary, deserialize-remote + targeted edge) vs `resync_after_native_edge` (native, re-mirror local). `push_cache` + `check_lock` retained for body/status/provenance/delete writes.
- WHY push-first (defect D): cache is the LOCAL mirror; remote is authoritative for the edge of record. Writing cache before a push that can fail -> divergence (cache linked, remote not). Push first -> cache only mutated on confirmed remote success -> cache never lies. Symmetric for unlink.
- DEDUP (defect C) is belt-and-suspenders: §1 insert-if-absent on remote merge + §2 insert-if-absent on cache write PREVENT new dups; §4 `fix relations` CLEANS legacy dups already on disk. All three use the same `(rel,target)` equality.
- TUI (defect B): both `LinkEditor` and `StatusPicker` previously swallowed write errors via `let _ =` and closed unconditionally -> a rejected link/status-change vanished with no feedback. The `error: Option<String>` + stay-open-on-error pattern is already proven by `CreateForm` (`submit_create_form` `:2422`) and `ProvenanceEditor`; this folds the two remaining overlays into it.
- Tests use `MockGhClient` at the gh seam: `with_view_issue` (source resync/merge fetch) and `with_graphql_responses` (membership). MockGhClient records `issue_edit` args -> the merge ACs assert on the exact `new_body` pushed.
- SCOPE GUARD: milestone relation-vocabulary constraint (defect E) is OUT -- separate iteration. NO field-level conflict detection, NO three-way text merge of prose (only the `related` edge is merged; concurrent prose edits are last-fetch-wins on the prose, untouched by the relation write). NO weakening of body-write protection. `--json` on `show`/`status` unchanged; the fix is entirely in the write + TUI overlay path. Verify after: `show RFC-N --json` `.related` reflects the edge with no duplicates.
